# 히스토리 설계

히스토리의 제품 불변 조건은 [`product-rules.md`](product-rules.md), 전체 책임 지도는 [`architecture.md`](architecture.md)를 참고하세요.

현재 `HistoryRepository`는 로드, 검색, 필터, 중복 확인, 추가·갱신, 교체 계약을 정의합니다. `SqliteHistoryRepository`가 서버 원본 구현이며 Next.js API를 통해 UI에 제공됩니다. `BrowserHistoryRepository`는 현재 v2 브라우저 기록의 일회성 전환 호환에만 남아 있습니다. 신원은 채널 ID, 확인된 정규 URL, 핸들, 확인 별칭, 정규화된 정확한 채널명 순서로 비교하며 검색·영상 URL은 신원으로 사용하지 않습니다.

히스토리는 사용자가 공급하거나 관리하는 파일이 아니라 애플리케이션이 확정 판정마다 자동 생성하는 내부 기억입니다. 자동 파이프라인은 안정적인 신원을 확보한 직후 SQLite를 확인합니다. 영구 하드 제외와 아직 유효한 판정은 근거 수집 전에 건너뛰지만, 동적 판정은 TTL 만료 또는 `rule_version` 변경 시 재검증 대상이 됩니다. 기본 재검증 주기는 동적 제외 45일, 보류 21일이며 설정에서 각각 30~60일, 14~30일 범위로 조정할 수 있습니다. 동일 실행 신원 블록리스트도 판정 전 적용합니다.

신규 채널의 모든 확정 판정은 자동 저장합니다. `fit_score`, 구성요소, 연락 준비 상태, 적용 설정, 규칙 버전과 다음 재검증 시각을 함께 저장합니다. 저장 경계의 반복·경합 쓰기는 새 레코드를 만들지 않고 동일 신원 레코드를 유지하며, 더 강한 신원 근거가 확인되면 기존 미확인 필드를 보강합니다. 사용자가 결과 화면에서 바꾼 판정은 `manual` 출처와 이유·메모·시각을 남기고 이후 자동 재평가보다 우선합니다. 다운로드 JSON은 `channel_name`, `url`, `status`만 제공하는 선택적 호환 출력이며 저장소 원본이나 입력이 아닙니다.

SQLite 스키마는 판정 레코드와 고유 신원 키를 분리합니다. 신원 키 고유 제약과 즉시 쓰기 트랜잭션이 반복·경합 쓰기의 중복을 방지합니다. v6은 점수·재검증 필드, v7은 수동 판정 감사 이력, v8은 마케터 승인부터 캠페인 성과까지의 후속 이벤트를 추가합니다. 마이그레이션은 버전 순서대로 트랜잭션 적용되고 `schema_migrations`에 기록됩니다. 데이터베이스 선택과 롤백은 [`decisions/006-sqlite-server-history.md`](decisions/006-sqlite-server-history.md)를 참고하세요.
