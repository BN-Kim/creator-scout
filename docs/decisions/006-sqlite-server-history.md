# 006 — H2 서버 히스토리에 SQLite 사용

## 상태

승인됨 — 2026-07-22

## 결정

H2의 서버 히스토리 원본은 `better-sqlite3`로 접근하는 로컬 SQLite 파일입니다. 기본 경로는 `.data/creator-history.sqlite`이고 `HISTORY_DATABASE_PATH`로 변경할 수 있습니다. Next.js API 경계만 데이터베이스에 접근하며 브라우저는 서버 API를 통해 기록을 읽고 씁니다.

스키마 변경은 `src/server/database/migrations.ts`의 순차 버전 마이그레이션으로 관리합니다. 각 마이그레이션은 트랜잭션 안에서 적용되고 `schema_migrations`에 기록됩니다. 히스토리 레코드는 판정, 사유 코드, 근거 요약, 실행 ID, 생성·수정 시각과 수동 교정을 보존합니다. 별도 신원 키 테이블의 고유 제약과 즉시 쓰기 트랜잭션으로 동일 신원의 중복 레코드를 막습니다.

## 이유

현재 단계는 단일 내부 Next.js 애플리케이션이며 외부 운영 인프라나 인증을 도입하지 않습니다. SQLite는 별도 데이터베이스 서버 없이 서버 영속성, 트랜잭션, 스키마 제약과 재현 가능한 테스트를 제공합니다. ORM은 현재 한 개 저장소에 불필요한 계층과 의존성을 추가하므로 도입하지 않습니다.

## 전환과 롤백

H2 이전 목 버전의 `creator-scout-history-v2` 브라우저 상태만 최초 서버 접근 때 검증 후 멱등적으로 자동 전송합니다. 서버 저장 성공 뒤에만 로컬 원본을 삭제하고 완료 표식을 기록합니다. 형식 오류나 서버 실패 시 로컬 원본을 그대로 유지합니다. 이는 사용자 기능이나 과거 파일 가져오기 경로가 아닙니다.

마이그레이션은 앞으로만 적용합니다. 운영 파일에 새 마이그레이션을 적용하기 전 SQLite 파일을 복사해 백업하고, 실패 시 애플리케이션을 중지한 상태에서 이전 코드와 백업 파일을 함께 복원합니다. 현재 v1 신규 데이터베이스는 파일을 제거하면 자동으로 빈 스키마를 다시 만들 수 있습니다. 데이터가 있는 파일을 삭제하는 방식은 롤백으로 사용하지 않습니다.

## 결과

SQLite 파일을 공유하는 Next.js 서버 인스턴스에서 브라우저와 기기에 관계없이 같은 히스토리를 조회합니다. 다중 서버·고가용성 배포가 필요해지면 저장소 계약 뒤에서 운영 데이터베이스 어댑터를 별도 결정해야 합니다.

히스토리의 자동 생성과 검증 전 중복 건너뛰기 원칙은 [`007-automatic-history-and-precheck.md`](007-automatic-history-and-precheck.md)가 정의합니다.
